# Backend — детали

Дополняет `../CLAUDE.md` (роли/права, архитектурные принципы, роадмап-статус — там). Этот файл
загружается только при работе с файлами внутри `backend/`: детальная схема данных,
мультитенантность и развёрнутые roadmap-заметки, которые не нужны при работе только с фронтом.

## Почему не Google Sheets
Исходно планировался Streamlit+gspread (Google Sheets как база) — простота и отсутствие инфраструктуры перевешивали. От этого отказались в пользу Postgres+FastAPI+React ради нормальной типизации данных, ролевой модели через JWT и SPA-интерфейса вместо Streamlit rerun-модели. Раздел "Структура данных" ниже описывает те же сущности, что раньше были листами Google Sheets — теперь это таблицы Postgres (см. `app/models.py`), но набор полей и связи между ними не менялись.

## Структура данных

Ниже — те же сущности, что раньше были листами двух Google Sheets-файлов (см. "Почему не Google
Sheets"). Теперь это таблицы одного Postgres, определённые в `backend/app/models.py`; разделения на
"файл с рабочими данными" и "закрытый файл с доступами" на уровне БД больше нет — это было решение
специфичное для ACL Google Sheets (права выдаются на файл целиком). Разграничение по ролям теперь
на уровне API (`require_roles`), не на уровне БД/файла.

**Company** — тенант (мультитенантность, добавлена 2026-07-16, см. отдельный раздел ниже)
Почти все остальные таблицы ниже несут `company_id` — исключение только RecipeItem (скоуп
транзитивно через recipe_id/material_id).

**Materials** — справочник сырья
Категория — свободная строка в БД (`String(20)`, без CHECK/enum). Базовая тройка кодов —
`тара`, `косм` (косметика), `свеч` (свечи) — так пришли из импорта «oinarri рецептуры», не
`сыпучее`/`жидкое`, как было в исходном плане (0 материалов с такими значениями на живых данных,
2026-07-21). `GET /api/ingredients/categories` отдаёт эту тройку + любые кастомные категории,
уже использующиеся в компании; `NewIngredientModal.tsx` даёт создать новую категорию прямо в форме
("Добавить категорию" после пунктирной черты в выпадающем списке) — свободный ввод, не ограничено
тройкой. Полное название на экране — через `materialCategoryLabel()` (`lib/labels.ts`), само
значение в БД не трогается. Категория «тара» в БД (`packaging_type` короб/флакон/наклейка/лента/
прочее) исторически смешивает два разных по смыслу понятия — см. разбор терминов ниже.

**Тара vs упаковка (термины, зафиксировано 2026-07-26, запрос Александра)** — раньше в проекте оба
слова использовались как синонимы, дальше это две разные сущности по назначению:
- **Тара** — презентационная ёмкость, которую видит покупатель (флакон, банка) — часть образа
  продукта, "глянцевая"/представительская.
- **Упаковка** — техническая составляющая для отправки контрагенту/защиты товара (короб, скотч,
  пузырчатая плёнка) — покупатель её не воспринимает как часть продукта.
В БД оба пока живут в одной категории материала `тара` (`packaging_type` короб/лента — по смыслу
это "упаковка" из термина выше, флакон/наклейка — "тара") — таксономия `packaging_type` не
переименована и не разделена на уровне схемы, это осталось долгом на будущее. Практическое
следствие сейчас — тара обязательно выбирается и списывается в момент **Производства** (см. ниже),
не в отдельном шаге/вкладке.
Архив (2026-07-21, тот же паттерн, что у Recipe) — архивный материал не попадает в список по
умолчанию (`GET /api/ingredients?archived=false`, дефолт) и не всплывает в "остатки ниже минимума"
на дашборде, но остаток/история движений/связи из RecipeItem не трогаются — фильтруется только
видимость. Переключатель Founder/Developer, см. `IngredientDetailPanel.tsx`.
Подкатегория тары (2026-07-23, запрос Александра) — `packaging_type` (короб/флакон/наклейка/
лента/прочее, `PACKAGING_TYPES` в `constants.py`) + типовые поля `width_mm`/`height_mm`/
`length_mm`/`volume_ml`/`material_finish`/`tape_feature`, осмысленны только при
`category="тара"`, справочные — в себестоимость не входят (та считается только по фактическим
поставкам, см. "Себестоимость по лотам"). Раздел «Упаковка» в сайдбаре (`/packaging`,
`PackagingMaterialsPage.tsx`) — теперь каталог тары с вкладками по `packaging_type`, а не журнал
упаковки продукта (см. ProductionLog ниже, тот функционал туда и перенесён). Создание —
`NewPackagingMaterialModal.tsx`, поля меняются формой в зависимости от выбранного типа.

**Transactions** — единый журнал движений сырья (сердце системы)
Остаток = сумма приходов − расходов ± корректировки, считается на лету SQL-запросом (не хранится статично).
`POST /api/production` перед списанием проверяет остаток каждого материала рецепта — если сырья не
хватает на запрошенное кол-во партий, возвращает 400 и не пишет ни одной транзакции (см. `production.py`).
`freight_cost` (2026-07-21) — доля транспортных расходов поставки, отнесённая на эту строку прихода;
`price` остаётся закупочной ценой поставщика без искажений. Заполняется только через групповой приход
(`POST /api/ingredients/income/batch`, см. "Себестоимость по лотам" ниже) — обычный одиночный приход
этого поля не трогает.

**Себестоимость по лотам** (2026-07-21, запрос Александра, `app/costing.py`) — принцип "дешёвый лот
первым": каждый приход — лот с ценой (закупка + доля `freight_cost`), расход съедает лоты по
возрастанию цены. Не отдельная таблица — считается на лету по истории Transaction того же материала,
как остаток. Корректировки в лоты не лезут (осознанное упрощение — не путают себестоимость, только
двигают остаток). `POST /api/ingredients/income/batch` — групповой приход нескольких материалов одной
поставкой + одна сумма транспортных расходов, делится между материалами пропорционально весу
(`min_purchase_batch_weight`/`min_purchase_batch_qty` с карточки материала; без этих полей — fallback
на пропорцию по количеству). Продукт → себестоимость партии/единицы = сумма по составу рецепта
(`RecipeItem.qty_per_batch` × себестоимость активного лота материала), показывается на карточке
продукта (`GET /api/products`, поля "себестоимость партии"/"себестоимость единицы"); `None`, если хотя
бы по одному материалу рецепта нет активного лота с ценой — не показываем частично посчитанную
цифру. **Ручного поля "себестоимость 1 шт" на карточке материала больше нет** (`Material.unit_cost`
удалён миграцией `d21082f74852`, 2026-09-13, запрос Александра: "у нас только реальные данные, без
мифов") — себестоимость считается исключительно по фактическим поставкам, без ручного фолбэка.

**Recipes** — рецепты
Поле «технология» добавлено при переносе реальных рецептов — пошаговая инструкция приготовления, у founder в исходнике была для каждого рецепта. Поле «категория» — выбор из уже существующих категорий Product (не свободный ввод, не отдельный справочник), состав рецепта обязателен при создании.
«Процент потерь» (2026-07-21, запрос Александра) — сверх точного расчёта по составу рецепта,
накидывается при списании сырья в `POST /api/production` (`loss_factor = 1 + loss_percent/100`,
умножает и проверку достаточности остатка, и саму сумму списания) и в расчёте себестоимости
продукта (`app/costing.py::compute_product_costs`) — иначе оба числа были бы занижены относительно
того, что реально уходит со склада. Дефолт 3% на уровне модели (`Recipe.loss_percent`,
`server_default='3'`) — глобальный старт, редактируется per-рецепт через `PATCH /api/recipes/{id}`
(`RecipeDetailPanel.tsx`, инлайн-редактирование, Founder/Developer). `PATCH /api/recipes/{id}`
теперь общий partial-update (`UpdateRecipeRequest`, `exclude_unset`), не только для archived —
переиспользуется тем же эндпоинтом, что и переключатель архива.

**RecipeItems** — состав рецепта
В Sheets-эпоху здесь дублировались "название рецепта"/"название материала" (Founder читала лист
глазами). В Postgres это лишний денормализованный столбец, который может разъехаться при
переименовании — таблица хранит только id, названия при чтении джойнятся из Recipes/Materials.

**Products** — готовые изделия (мыло, свечи и т.д.), карточка товара
Обязательные при создании: название, категория, GTIN (`app.constants.PRODUCT_REQUIRED_FIELDS`).
Остальное опционально. "Название рецепта" в БД не хранится — джойнится через `recipe_id` при чтении
(см. `app/routers/products.py`). "Себестоимость партии"/"себестоимость единицы" — не хранятся,
считаются на лету при каждом чтении (см. "Себестоимость по лотам" выше). Категория продукта —
свободный ввод только через `CategorySelect.tsx` (2026-07-26, запрос Александра: раньше был голый
`<input>` без подсказок, из-за чего накопились дубли вида "крем"/"Уходовая косметика" в реальных
данных) — строгий выбор из существующих (до 5 в списке) + "Добавить категорию", не печатать
руками. `default_packaging_material_id` (2026-07-26) — см. ProductionLog ниже, память последнего
выбора тары для этого продукта, не жёсткая привязка.

**Counterparties** — контрагенты-покупатели (юрлица)
Заполняются Founder/Developer в разделе «Контрагенты» и привязываются опционально к Sale при отгрузке.
Автоподстановка по ИНН (2026-07-19) — `GET /api/counterparties/lookup?inn=` ходит в
suggestions.dadata.ru (`app/config.py::DADATA_API_KEY`, пусто по умолчанию → 501, фронт
тихо остаётся в обычном ручном режиме, ничего не ломает). На успехе фронт
(`NewCounterpartyModal.tsx`) блокирует найденные поля (название/КПП/ОГРН/адрес) от
ручного редактирования — просьба Founder исключить случайные опечатки при заведении
контрагента; «Ввести вручную» снимает блокировку, если DaData ошиблась/устарела.

**Sales** — продажи готовых изделий
`POST /api/sales` проверяет «готово к отгрузке» продукта (см. `products.py::_packaged_by_product`) —
если продано больше, чем упаковано минус уже проданное, возвращает 400. Продукты без `recipe_id`
(не привязаны к рецепту) проверке не подлежат — для них «готово к отгрузке» не считается.
Полный пайплайн (2026-07-23, решение Александра): рецепт → производство (списание сырья) →
упаковка → «готово к отгрузке» → отгрузка. До этого база была ProductionLog (сырое изготовление,
без учёта упаковки) — переключено на PackagingLog, т.к. Production и Packaging слились в одну форму
в тот же день (см. ProductionLog ниже) и товар физически готов к отгрузке только после упаковки.
Блокировка от гонки при одновременных продажах (2026-07-21, code-review) раньше лочила строку Recipe
как прокси-мьютекс — теперь лочит сам `Product` (осмысленнее: готовность больше не завязана на
рецепт, только на product_id через PackagingLog).

**ProductionLog** — журнал смен производства
Источник данных для КПД. КПД = количество партий + скорость (время на партию) + брак/ошибки.
`GET /api/production/leaderboard` — отдельный «лидерборд»-эндпоинт (не dashboard/kpi): кол-во
произведённого (партии×выход_партии − брак) за сегодня и с начала месяца по каждому сотруднику,
доступен ВСЕМ ролям включая worker (осознанное решение Founder — мотивация, все видят, кто сколько
делает). Отдаёт только количество — цен/выручки в ProductionLog нет вообще, изоляция не на фронте,
а в том, что этих полей физически нет в ответе. Не путать с `dashboard/kpi` (founder/developer,
полная история помесячно) — тот остаётся закрытым, там нет такого ограничения по данным.
Изготовление + упаковка одной формой (2026-07-23, запрос Александра) — `POST /api/production`
принимает опциональные `packaged_qty`/`packaged_defects` вместе с обязательным `product_id`
(раньше был не обязателен — recipe_id выводился из выбранного продукта на фронте, но сам id
продукта не передавался); если `packaged_qty > 0`, тем же запросом пишется отдельная строка в
PackagingLog (см. ниже, модель не изменилась). Раньше это было отдельной вкладкой/журналом —
теперь `NewProductionModal.tsx` покрывает оба шага одной формой.
**"Упаковано: Да/Нет" обязательный выбор (2026-07-26, запрос Александра)** — заменил старый
опциональный блок "Упаковка (необязательно)". Дефолт "Нет" (`packaged_qty=0`) — продукт остаётся
в журнале Производства с бейджем «Не упаковано» (`ProductionLog.packaged=false`), не готов к
отгрузке. "Да" — раскрывает выбор **тары** (`MaterialCombobox` по каталогу материалов категории
`тара`, см. Materials выше — не "упаковки" в новом терминологическом смысле, см. разбор терминов)
+ кол-во (по умолчанию = произведено−брак, редактируется) + брак упаковки (было и раньше).
`ProductionLog.packaged` — снимок этого выбора на момент записи (`body.packaged_qty > 0`), не
джойн по PackagingLog: между таблицами нет FK друг на друга, а определять "упаковано ли" по
product_id+дате было бы ненадёжно при нескольких партиях в один день. Списание тары — тот же
принцип, что у сырья рецепта: row-lock (в одном лок-сете с материалами рецепта, чтобы не ловить
deadlock), проверка остатка ДО записи (400 без частичного списания, если не хватает), Transaction
(EXPENSE) на весь `packaged_qty` (не за вычетом брака упаковки — бракованная упаковка тоже
физически съела тару, тот же принцип что в `_packaged_by_product`). `Product.
default_packaging_material_id` — тара, выбранная в прошлый раз для этого продукта, предзаполняет
форму при следующем внесении производства (`GET /api/production/products` отдаёт её вместе со
списком) — не жёсткая привязка/рецепт, просто подсказка, воркер может сменить каждый раз.
Автоподбор тары по размерам продукта — отложено, сам Александр сказал "в последствии".

**PackagingLog** — журнал упаковки (модель), больше не отдельный раздел меню
Фиксирует момент упаковки готового изделия после производства — отдельный шаг от ProductionLog
(производство сырой партии) и Sale (отгрузка). С 2026-07-23 это ИСТОЧНИК расчёта «готово к
отгрузке» у Product (см. `app/routers/products.py::_packaged_by_product`) — раньше считалось от
ProductionLog, теперь от PackagingLog (см. Sales выше, там же история решения). `POST /api/packaging` (роутер
`packaging.py`) оставлен как есть (не удалён, backward-compat/API-полнота), но с 2026-07-23 не
используется UI напрямую — запись через него теперь создаёт `POST /api/production` (см. выше).
Раздел «Упаковка» в сайдбаре (`/packaging`) для этого журнала как отдельной вкладки БОЛЬШЕ НЕТ —
пункт меню переиспользован под каталог тары (см. Materials выше), история упаковки читается через
`GET /api/packaging`, встроена в `ProductionPage.tsx` вторым блоком ("История упаковки") под
основным журналом производства. `material_id` (2026-07-26) — какая именно тара ушла на эту
упаковку; nullable — старые строки (до миграции) и записи с `qty=0` тару не несут.

**Feedback** — обратная связь для разработчика (реализовано 2026-07-26, `app/routers/feedback.py`)
+ **FeedbackAttachment** (`feedback_id, image_base64, filename`, до 3 на сообщение, без своего
`company_id` — скоуп транзитивно через `feedback_id`, тот же паттерн, что у RecipeItem).
`POST /api/feedback` — отправить может ЛЮБАЯ авторизованная роль (worker включительно), форма на
`/feedback` (пункт «Обратная связь» в меню профиля, видна всем ролям, не гейтится как
Сотрудники/Техпанель). **`GET /api/feedback` (список) и `PATCH /api/feedback/{id}` (смена статуса)
— только Developer, НЕ Founder** — сообщение адресовано конкретно разработчику, это не общий
баг-трекер компании.
UI-панель разбора входящих обращений **переехала с `TechPanelPage.tsx` на саму `/feedback`**
(2026-07-27, повторное решение Александра, отменяет более раннее "давай у него в меню и
оставим это, в тех панели") — путал свою личную историю обращений (эта же страница, форма +
"Актуальные"/"Решённые") с панелью разбора чужих в Техпанели, оказалось на двух разных
страницах без видимой связи. Теперь `/feedback` зонирована вкладками **"Отправленные"/
"Полученные"** (`FeedbackPage.tsx`) — вторая вкладка видна только Developer, содержит то, что
раньше было в Техпанели один в один (автор+роль, полная дата-время, `<select>` смены статуса,
вложения). `TechPanelPage.tsx` больше не тянет `/feedback` вообще.
Вложения — скриншоты, до 3 шт/сообщение, до `FEEDBACK_MAX_ATTACHMENT_BYTES` (8 МБ) каждый,
хранятся как PNG в Postgres (тот же паттерн, что `SurveillanceScreenshot`) — видео явно отложено
до платного сервера/object storage (см. skill `deferred-topics`). `_normalize_to_png()` перекодирует
любой присланный файл в чистый PNG вместо доверия исходным байтам (снимает полиглоты/встроенные
скрипты под видом картинки), сжимает до `FEEDBACK_MAX_DIMENSION` (2560×1440), не ужимая ниже
`FEEDBACK_MIN_DIMENSION` (1280×768) — снимок должен остаться читаемым. Decompression-bomb защита —
явная проверка `width*height` ДО `.load()` (дефолтный `Image.MAX_IMAGE_PIXELS` Pillow между 1x-2x
порога только предупреждает, не блокирует — однотонная PNG 8000×8000 весит ~200КБ на диске, но
64М пикселей в памяти). Имя файла обрезается до 255 символов до INSERT (колонка `String(255)`,
Postgres не обрезает VARCHAR молча). Rate-limit 20/час на пользователя (`check_rate_limit`, тот же
in-memory лимитер, что у публичной регистрации).
**Список "своих" обращений + уведомление автору** (2026-07-26, запрос Александра) — `GET
/api/feedback/mine` (любая роль, только свои по `author_id`), рендерится на `/feedback` под формой,
разбит на "Актуальные"/"Решённые". Полноценного push/websocket в приложении нет — "уведомление"
это дружелюбная текстовая строка `статус для автора`, посчитанная на бэке (`_AUTHOR_STATUS_MESSAGE`
в `feedback.py`) по текущему статусу: "Спасибо за Ваше обращение, оно в работе" при переходе в
"просмотрено", "...оно решено!" при "решено" — автор видит её при следующем визите на страницу, не
отдельный канал (email/Telegram и т.п. не подключены).

**Users**
Учётные записи создаёт только Founder (или Developer) через интерфейс приложения. Раньше это был
физически отдельный Google Sheets-файл (права выдаются на файл целиком) — в Postgres это обычная
таблица в той же БД, изоляция обеспечивается на уровне API (`require_roles`), не на уровне БД.
Телефон валидируется на бэке (`app/schemas.py`) — только цифры и `+ - ( )`, буквы отклоняются.

**LoginLog** — журнал входов (кто и когда авторизовался)
Пишется на каждый успешный `POST /api/auth/login`. Список (`GET /api/auth/log`) виден только
Founder/Developer — выводится в разделе «Сотрудники».

## Мультитенантность (добавлена 2026-07-16)

Проект перешёл от однотенантной мастерской к изоляции нескольких независимых компаний в одной
БД — Founder решил попробовать пустить сюда не только свою мыловарню, но и, например, 3Д-печатную
мастерскую (вариант А из обсуждения — реальная изоляция, не просто общность модели данных).

- **Company** — тенант. `company_id` есть почти на каждой таблице (см. "Структура данных").
- **Онбординг новой компании — два пути.** (1) `POST /api/companies` (`app/routers/companies.py`,
  2026-07-18) — Developer заводит компанию прямо из приложения (пункт «Компании» в меню профиля,
  только у Developer, Founder такого пункта не видит вообще). Создаёт компанию + сразу первого
  **Developer**-аккаунта этой компании — НЕ Founder, того заводит тот же разработчик отдельно после
  (через `create_founder.py --company-id`, п.2 ниже, или это станет отдельной кнопкой позже). Это
  единственный роутер, намеренно не фильтрующий по `user["company_id"]` — вся его задача cross-tenant
  (список всех компаний + создание новой), см. "Архитектурные принципы" п.5 в корневом CLAUDE.md. (2) CLI-скрипт
  `backend/scripts/create_founder.py` остаётся для бутстрапа первой компании на чистой БД (там ещё
  некому зайти в интерфейс) и для добавления второго Founder к уже существующей компании:
  `python -m scripts.create_founder --company-name "Новая мастерская" --fio "..." --login ... --password ...`
  (или `--company-id <id>` вместо `--company-name`, не плодя дубликат компании).
  Оба пути — **не** самостоятельная регистрация: требуют существующего Developer-аккаунта с доступом
  к приложению/БД, не публичная форма (та отдельная, описана ниже — "Публичная self-serve
  регистрация").
- **Логин глобально уникален** (не per-company) — экран входа не спрашивает "какая компания", она
  определяется автоматически по аккаунту. `company_id` живёт в JWT-payload наравне с ролью (см.
  "Архитектурные принципы" п.4 в корневом CLAUDE.md) — не перечитывается из БД на каждый запрос.
- **Раскладка дашборда** (`DashboardWidgetLayout`) — per-user с 2026-07-20 (была общая на всю
  систему до мультитенантности, затем per-company; см. п.7 роадмапа ниже) — уникальность
  `(company_id, user_id, widget_key)`.
- **Изоляция проверяется явно** — `backend/tests/test_multitenancy.py`, отдельный файл, не
  разбросано по остальным тестам. Кросс-компанийный доступ по чужому id всегда 404 (не 403) —
  не подтверждаем даже факт существования чужой записи.
- Первая компания (существующая мастерская, "oinarri") — результат бэкфилл-миграции
  `a772deab8f2a_multi_tenant_company_id.py`, фиксированный id `a0000001`.
- **Публичная self-serve регистрация** (2026-07-18, реализована) — `POST /api/auth/register`
  (`app/routers/auth.py`, без `require_roles`/`get_current_user` — второй такой публичный
  POST-эндпоинт в приложении, первый — `POST /api/public/workshop-ping/{token}`, см. "Роли и
  права" → "Ограничение входа worker'ов по сети мастерской" в корневом CLAUDE.md, там токен сам себе авторизация),
  `RegisterPage.tsx` на `/register`. Создаёт компанию + первого **Founder**-аккаунта
  (не Developer — тот только для internal-онбординга, `POST /api/companies` выше) и сразу логинит
  (тот же `{access_token, user}`, что и `/login`). Переиспользует `attach_or_create_membership` —
  если введённый логин уже существует у другого человека, привязывает его Founder'ом новой компании
  (тот же "вариант А", тот же пароль-чек). Обязательные поля: название компании, ФИО, телефон, логин,
  пароль — телефон с прицелом на будущую SMS/Telegram-верификацию, сам механизм которой пока не выбран
  (см. ниже). Rate-limit 5/час по IP (`app/rate_limit.py`, in-memory, читает `X-Forwarded-For` — Render
  проксирует, `request.client.host` был бы IP прокси, не посетителя, security-review 2026-07-18 поймал
  до пуша). Капчи пока нет — осознанная задолженность (см. ниже). Публичный анонимный эндпоинт ловит
  400 от `attach_or_create_membership` и подменяет сообщение на общее — "неверный пароль" и "уволен"
  по отдельности превратили бы эндпоинт в оракул для перебора чужих логинов (тот же security-review).
  `RegisterCompanyRequest` (`schemas.py`) — `max_length` на company_name/fio/login (совпадает с длиной
  колонок Postgres — без этого анонимный запрос ронял бы 500 вместо чистого 422, SQLite в тестах эту
  ошибку не ловит, маскировала баг) и байтовая (не символьная) проверка пароля ≤72 байт — bcrypt≥4.2
  кидает `ValueError` на пароле длиннее, кириллица 2 байта/символ. Тесты — `test_register.py`, включая
  отдельный regression на изоляцию данных нового тенанта (не полагается только на общий механизм в
  `test_multitenancy.py`).
  **Задолженность (сознательно, не блокирует первый заход):** капча (hCaptcha/Turnstile — оба
  бесплатные), телефон собирается, но не верифицируется — механизм (SMS-код или через Telegram-бота,
  требует своего бота + Telegram-аккаунт у клиента) ещё не выбран Founder'ом.

## Мульти-компанийные пользователи (добавлена 2026-07-18)

Founder попросил: один и тот же человек (сначала — сам разработчик как Developer, но
потенциально и Founder/Worker) может обслуживать/работать сразу в нескольких компаниях,
без необходимости заводить отдельный логин на каждую.

- **CompanyMembership** (`app/models.py`) — связь user↔company↔role, `unique(user_id, company_id)`.
  `User` больше НЕ несёт `company_id`/`role` напрямую (были там до 2026-07-18, перенесены сюда
  миграцией `2963dcbe68c7_company_memberships.py`) — `User` теперь чистая личность (ФИО, логин,
  пароль, `status`, телефон/мессенджер/адрес/документ). **Все эти поля остаются глобальными на
  User** (уволен = уволен из всех компаний сразу; смена телефона/ФИО/документа в одной компании
  видна во всех, где состоит человек) — осознанное решение: это один реальный человек с одним
  именем/паспортом/телефоном в жизни, не разные личности по компаниям. Per-membership копии этих
  полей не запрашивались и не сделаны.
- **Вход с одной компанией** (99% пользователей) — не меняется ни на бит: `POST /api/auth/login`
  сразу отдаёт `access_token` + `user`, как и раньше.
- **Вход с несколькими компаниями** — `authenticate()` (`app/security.py`) не логинит сразу,
  отдаёт `{needs_company_choice: true, pending_token, companies: [...]}`. Фронт (`LoginPage.tsx`)
  показывает список компаний вместо навигации; `POST /api/auth/select-company` с `pending_token`
  + выбранным `company_id` финализирует вход. `pending_token` — отдельный короткоживущий (5 мин)
  JWT-тип (`PENDING_TOKEN_TYPE`), не полноценная сессия — годится только на этот один эндпоинт.
- **Переключение компании уже залогиненным** — `POST /api/auth/switch-company`, без повторного
  пароля (личность уже подтверждена), просто переиздаёт токен на другое членство того же
  человека. В сайдбаре (`Sidebar.tsx`) — блок «Другие компании» в меню профиля, виден только
  если у юзера больше одного членства.
- **JWT payload несёт `companies: [{id, name, role}]`** — список ВСЕХ компаний юзера, не только
  активной, посчитан на момент выдачи токена. Как и `role`/`company_name`, не перечитывается из
  БД на каждый запрос (см. п.4 архитектурных принципов в корневом CLAUDE.md) — смена состава компаний применяется
  только после переиздания токена (следующий логин/переключение), тот же осознанный компромисс.
  `get_current_user` фоллбечит на `[текущая компания]`, если поля нет (токены до 2026-07-18).
- **Существующий логин при создании — не ошибка, а приглашение** (вариант А, решение Founder),
  единый helper `attach_or_create_membership` (`app/security.py`) — используется в
  `POST /api/companies`, `POST /api/users` и `create_founder.py`, не три отдельные копии.
  Если введённый логин уже существует у другого человека:
  - **Требует правильный пароль существующего аккаунта.** Без этой проверки любой Founder/
    Developer мог бы привязать ЧУЖОЙ аккаунт к своей компании, зная только логин (не пароль),
    и через `reset-password` перехватить ГЛОБАЛЬНЫЙ пароль — это была реальная дыра, поймана
    security-review 2026-07-18 до пуша в прод, не гипотетическая. Пароль в форме поэтому НЕ
    игнорируется (в отличие от ФИО/телефона и т.п. — те действительно игнорируются, у
    человека уже есть свой аккаунт).
  - **Уволенный существующий аккаунт (status ≠ активен) — отклоняется**, не привязывается
    молча. Без этой проверки founder думал бы что "нанял" рабочего, а тот не смог бы зайти
    (status глобальный, увольнение из одной компании блокирует все).
  - Дубликат (тот же user_id уже состоит в ТОЙ ЖЕ компании) — по-прежнему ошибка 400.
  - Фронт (`NewStaffModal.tsx`/`NewCompanyModal.tsx`) показывает предупреждение, если бэк
    вернул `attached_existing: true` — иначе founder не узнал бы, что "новый сотрудник" на
    самом деле уже существующий человек, а не свежесозданный аккаунт.
- **Сброс пароля** (`POST /api/users/{id}/reset-password`) меняет пароль на `User`, то есть сразу
  во ВСЕХ компаниях, где состоит человек — это осознанное поведение (один пароль на личность),
  не баг.
- **`get_current_user` отклоняет `pending_token`** явно (проверка `payload.get("type")`) — без
  этой проверки pending-токен проходил `jwt.decode` как обычный и падал `KeyError`→500 вместо
  чистого 401 (был баг, пойман code-review 2026-07-18 до пуша).
- **`switch-company` тоже пишет `LoginLog`** (той компании, куда переключились) — иначе
  Founder/Developer этой компании не видел бы в истории входов доступ через переключалку,
  только через прямой логин.
- Тесты: `test_multi_company_login.py` (вход/select-company/switch-company, включая отказ
  чужого pending_token и обычного access_token вместо pending), `test_companies.py` и
  `test_users.py` (вариант А — привязка существующего логина, неверный пароль отклоняется,
  уволенный существующий аккаунт отклоняется).
