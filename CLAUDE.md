## Что за продукт
Внутренняя система для небольшой мастерской (мыло, свечи, косметика ручной работы):
- инвентаризация сыпучего и жидкого сырья (раз в месяц, возможно чаще)
- учёт расходов и пополнений сырья
- учёт производства партий по рецептам со списанием сырья
- учёт продаж готовых изделий
- КПД сотрудников по сменам
- дашборд с аналитикой
- Telegram-бот для быстрых запросов (низкий приоритет, см. "Роадмап реализации" п.9)

Требование к простоте интерфейса: должно быть управляемо человеком без технического бэкграунда ("любая обезьяна должна справиться"). Рядовой сотрудник не видит и не знает о существовании базы данных/API — только страницы React-приложения.

## Технический стек
Sync (не async) SQLAlchemy + psycopg3, все роуты через `def`, не `async def` — осознанный
выбор, не долг (2026-07-27, подтверждено на code-review): FastAPI гоняет sync-роуты в
threadpool (~40 потоков по умолчанию), async даёт выигрыш только когда параллельных
запросов больше размера пула — при масштабе на несколько сотрудников одной мастерской
этого не происходит, реальный прирост скорости от переписывания на async ≈ 0%, риск
перепроверки всех 250 тестов и 16 роутеров не окупается. **Пересмотреть, когда компаний
станет больше 5** — тогда параллельная нагрузка может приблизиться к порогу, где async
действительно быстрее.

Worker НЕ видит чужой полный КПД (dashboard/kpi — история, брак, финансы) и вообще не знает о
существовании базы данных/API — работает исключительно со страницами React-приложения. Исключение —
production/leaderboard (см. ProductionLog в `backend/CLAUDE.md`): осознанно открытая всем ролям витрина только
количества произведённого за сегодня/месяц, отдельная от закрытого dashboard/kpi.

**Founder не может назначить роль Developer** (2026-07-21, code-review) — `POST /api/users` и
`PATCH /api/users/{id}` раньше проверяли только, что `role` вообще существует в `USER_ROLES`, не
кто её назначает: Founder мог создать себе Developer-аккаунт и получить Техпанель/Компании в обход
таблицы ролей выше. Теперь `role == DEVELOPER` в теле запроса требует, чтобы вызывающий сам был
Developer, иначе 403.

**Ограничение входа worker'ов по сети мастерской** (2026-07-23/24, запрос Александра, опционально
по компании) — настраивается на `StaffPage.tsx` (`GET/PUT /api/users/network-settings`,
founder/developer). Изначально (2026-07-23) было через DDNS-хостнейм, резолвящийся на каждый
вход — **переделано 2026-07-24 на call-home/heartbeat**, т.к. DDNS-провайдеры (DuckDNS и
подобные) часто недоступны из РФ. Механика: `POST /api/public/workshop-ping/{token}` — публичный
эндпоинт без авторизации (128-битный токен в пути сам по себе авторизация, `secrets.token_hex(16)`,
генерится лениво при первом включении в `PUT /api/users/network-settings`), роутер мастерской
стучится сюда раз в несколько минут (cron), сервер запоминает `Company.worker_network_ip` = IP
звонившего (виден автоматически из самого HTTP-запроса, `rate_limit.py::client_ip`, тот же
X-Forwarded-For-парсинг, что у rate-limit) + `worker_network_ip_updated_at`. `security.py::
enforce_workshop_network` на каждом входе (`/login`, `/select-company`, `/switch-company`) просто
сверяет IP запроса с последним записанным — без DNS вообще. `Company.worker_network_enabled` —
явный тумблер, отдельный от наличия IP (можно включить раньше первого пинга). Fail-closed: нет
IP, или последний пинг старше 15 минут (`_WORKSHOP_PING_STALE_MINUTES` в security.py — роутер
считается недоступным) — отклоняем вход, не пропускаем молча. Только для роли `worker`,
founder/developer не ограничены (может понадобиться доступ удалённо). На роутере ничего
устанавливать не нужно — `curl`/`uclient-fetch` есть в стоке OpenWrt, команда для cron с готовым
токеном показывается прямо на `StaffPage.tsx`.

## Архитектурные принципы, которые нельзя нарушать
1. Ни один прямой доступ/ссылка на БД не должен быть виден в интерфейсе Worker.
2. Проверка роли — на каждом роутере программно (`require_roles(...)` в `app/security.py` как FastAPI-зависимость), а не только скрытием пункта меню на фронте — иначе можно обойти через прямой запрос к API.
3. Пароли — только bcrypt-хэш, никогда plaintext.
4. JWT — секрет только из `JWT_SECRET` (env), никогда не хардкодить. `get_current_user` перепроверяет статус пользователя в БД на каждый запрос (уволенный теряет доступ сразу, не дожидаясь истечения токена) — роль, `company_id` и `company_name` при этом берутся из payload токена, не перечитываются из БД, так что смена роли/компании/названия компании применяется только после переиздания токена (следующий логин), это осознанный компромисс, не баг (пользователь и так не переезжает между компаниями на практике). `company_id`/`company_name` — оба обязательны, отсутствие любого из двух форсирует чистый 401 (не просто одного `company_id`) — иначе фронтовый фоллбек на вайт-лейбле мог показать чужой бренд компании, у которой токен не нёс company_name (см. "Мультитенантность" в `backend/CLAUDE.md`).
   **2026-07-21, найдено на code-review и подтверждено вживую на проде:** `JWT_SECRET` не был
   выставлен в Render env — приложение молча работало на захардкоженном dev-фоллбеке
   (`app/config.py`), а значит подделать токен под любой ролью/компанией мог любой, кто читал
   этот файл. `app/config.py` теперь падает при старте (`SystemExit`), если `JWT_SECRET` не
   задан и `RENDER=true` в env (Render сам его проставляет на каждый сервис — надёжный признак
   "не локалка"); локальный dev-фоллбек остаётся только вне Render. Секрет добавлен в Render
   Environment после находки — все существовавшие на тот момент токены (включая подделанные
   старым фоллбеком) стали недействительны, каждому потребовался повторный вход.
   `_find_user`/`attach_or_create_membership` также раньше искали логин через `ilike()` —
   `%`/`_` в самом логине трактовались как SQL-wildcard, открывая перебор существующих логинов
   через паттерн-матчинг (и позволяя завести аккаунт с буквальными `%`/`_` в логине). Заменено
   на точное регистронезависимое сравнение (`func.lower(User.login) == ...`). Заодно закрыт
   time-based оракул в `authenticate()` — путь "логина не существует" теперь тоже прогоняет
   `bcrypt.checkpw` (против фиктивного хэша), а не завершается мгновенно до вызова bcrypt, чтобы
   время ответа не отличало существующий логин от несуществующего.
5. Мультитенантность: каждый роутер обязан фильтровать ВСЕ запросы по `user["company_id"]` и проставлять его при создании записей — утечка данных между компаниями через забытый фильтр является критическим багом, не обычным. RecipeItem — единственное исключение без своего company_id (скоуп транзитивно через recipe_id/material_id, оба проверяются на принадлежность компании при создании/изменении состава).

## Как со мной общаться (предпочтения пользователя)
- Обращение на "ты", тон дружелюбный, профессиональный, без воды
- Код сразу готовый к копированию, с лаконичными комментариями
- Если задача сложная — сначала коротко архитектурное решение, потом реализация
- **Работа идёт через Telegram-мост (2026-07-21, жёсткое правило, повторялось 6+ раз, каждый
  раз с потерей времени Александра).** Простой текстовый вывод ассистента НЕ доходит до
  Telegram-чата — доходит только явный вызов инструмента `mcp__plugin_telegram_telegram__reply`
  (или `edit_message`). **На КАЖДОЕ сообщение от Александра — первым делом, до какой-либо
  работы — отправь короткое подтверждение через `reply`**: "принял, делаю X" ИЛИ, если есть
  неясности, сразу задай уточняющие вопросы этим же `reply`-сообщением (никогда не
  `AskUserQuestion` в этом контексте — не долетает). Финальный результат — тоже отдельным
  `reply`. Правило не опционально и не зависит от того, длинная задача или короткая: пропуск
  этого шага для Александра неотличим от "сообщение не дошло", он теряет время, ожидая ответ,
  которого не будет. Если в рамках одного ответа не было ни одного вызова `reply` — ответ не
  считается завершённым.
